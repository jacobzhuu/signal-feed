# ColdFuse 首次访问延迟排查与修复

2026-10-30。本次完成代码、隔离测试与测量，未部署、未重启生产8765服务、未写生产用户反馈、未训练或晋升模型。前端构建输出到 `artifacts/cold-latency/after/frontend`，没有覆盖生产 `frontend/dist`。

## 证据与结论边界

用户确认较慢的浏览器使用 Security / Science 兴趣，且普通推荐已显示后再切换兴趣加速。生产只读快照中，`f552d224` 身份确有该兴趣与3篇阅读历史；`4ab93890` 的兴趣和历史不同。Chrome账号不是服务端分流条件，匿名 Cookie、兴趣、历史和缓存状态才是。

旧访问日志只有URL与状态码，没有请求耗时或阶段耗时。`f552d224` 在01:43:59的请求至首次曝光相差约11秒，但曝光还受页面可见性、用户操作与前端1秒门槛影响，**不能把它当作HTTP耗时**。该次状态为 research，不是 timeout-fallback。此前01:05:46的 timeout-fallback 至首次曝光约3.09秒，也不能据此解释另一次几十秒等待。

已实测并修复的长等待机制：

1. `cold_serving.recommend` 原先同步调用 `service.refresh()`，目录陈旧时可能在当前请求上执行目录编码；暖目录的refresh锁虽然非阻塞，取得锁的首个请求仍同步完成刷新。
2. 目录编码与兴趣编码共用 `encode_lock`。原 `encode_query` 在取得锁后才查缓存，连已缓存的兴趣也会等待目录编码或其他查询。新用户无兴趣/历史时直接走热门路径，避开兴趣编码及研究进程；有兴趣或历史的用户路径不同。
3. 研究worker的2秒限制仅覆盖提交任务后的 `Event.wait`。模型身份内容校验、缓存键计算、锁及进程启动都在该等待之前；30秒子进程硬期限也不是整个HTTP请求的期限。
4. 前端加载新列表时隐藏原列表，使任何后台等待表现为内容区空白。没有发现按Chrome账号区分请求的代码。

**正常实测未自然复现几十秒等待；通过受控编码锁占用和校验I/O延迟复现了同类阻塞。不能宣称旧日志已唯一证明用户现场的具体阻塞阶段。** 新增的阶段计时用于后续上线后的现场确认。

## 同条件前后测量

使用冻结的2571篇公开文章目录、相同真实编码器/ColdFuse/SID权重、独立SQLite及合成身份。`SIGNALFEED_TEST_EVENTS=1`；所有模型只做读取与推理。修复前源码保存在 `artifacts/cold-latency/before/src`。故障注入只在隔离进程中进行。

暖请求增加约9–19ms的调度/计时开销，仍在几十到数百毫秒；本次不能声称毫秒级零退化。共享主机、一次完整前后运行的数据不是容量保证或统计显著性结论。

另用两个独立Chromium上下文与隔离HTTP服务测量“点击→响应→卡片显示后两帧”：

- 研究进程冷启动：2160ms → 2100ms。
- 暖进程的首个个性化请求：210–330ms → 210–331ms。
- 暖进程缓存命中：129–132ms → 145–148ms。
- 零历史无兴趣：修复后约106–113ms。
- 接收响应后的渲染/两帧等待：约21–49ms；无页面JS异常。

| 研究模型身份内容校验 | 约12.6–13.4ms |
| 个性化缓存键构造 | 约14.8–15.9ms |
| 首次生成模型加载（子进程） | 638ms |
| 首次ColdFuse ranker加载（子进程） | 593ms |
| 目录SID量化（子进程） | 11ms |
| 实际生成推理（子进程） | 16–20ms |

阶段有嵌套，不能直接把所有行相加。初始全目录和编码器预热约13.5–14.6秒；这发生在测试服务接收请求前，**不是新匿名用户首次访问时间**。正常测量证明生成推理本身并非几十秒级。

新增 `Server-Timing` 及 `ColdFuse timing` 服务日志：`session_db`、`queue`、`catalog`、`profile_db`、`profile_encode`、`base_recall_fusion`、`research_wait`、`online_rank_sort`、`snapshot_db`、`server_total`。不输出用户ID、兴趣文本或向量。浏览器前后对比测量时会话/排队尚使用合并标签 `queue_session`，最终代码拆分两项且已通过API回归。`server_total` 不含客户端网络和渲染时间，research_wait包含完整研究调用，不等于纯生成推理。

## 改动与隔离保证

- `serving.py`：兴趣缓存先读；ColdFuse使用后台目录刷新；未缓存画像等待最多150ms。单个服务最多一个后台画像任务和一个后台刷新任务，同文本复用在途任务，其他文本不复用错误向量。
- `background.py`：有界后台任务，无无限排队；任务未完成一直占用名额，等待超时不释放名额以虚增容量。
- `cold_serving.py`：为完整研究调用加上最多2秒的外层等待；按2.4秒计算研究剩余预算，最多8个在途调用。画像未就绪、研究繁忙、异常或超时均返回明确状态的基础推荐。现有30秒子进程硬期限继续有效。
- 研究payload增加user_id，使不同身份即使暂时画像相同也不共享个性化结果缓存；原兴趣、历史、文章顺序、目录向量、资格掩码、协同分数、热度和模型版本仍参与原内容哈希。没有取消模型内容校验或改变ColdFuse离线算法、权重、融合及特征契约。
- `api.py`：记录阶段计时；原请求/事件/快照关系和测试身份排除规则保留。
- 前端：加载时保留上一列表并明确标注；画像未就绪时如实提示“先展示基础推荐”，更新后按新request_id记录事件。

## 验证与未覆盖风险

42项后端/API/隔离/快照/worker回归通过；最终计时标签调整另复核3项；离线与在线策略一致性等4项复核。8项Playwright加载/竞态测试通过。TypeScript、独立目录Vite构建、Ruff和diff空白检查通过。没有运行训练或晋升测试。

目标3秒在本次正常和受控故障测量中达到，但不是所有故障的绝对SLA：系统/网络停顿、SQLite长时间锁等待、线程池整体耗尽、在线模型磁盘I/O等仍可能超预算。进程刚启动且尚无完整目录时快速返回503和Retry-After，需等服务ready，不会为凑延迟指标返回伪造内容。后台依赖永久卡住时只保留有限任务、继续回退，线程本身不能强制杀死。

当前生产仍为原进程；修复未上线，用户现场恢复尚未验证。后续获准部署后，应在两个真实Chrome身份上采集Server-Timing和浏览器Network Timing，确认是否仍有网络、扩展或其他浏览器因素。
