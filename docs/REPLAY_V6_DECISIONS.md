# 剖析后的固定实现选择

剖析源码 `edeb8da`，原始数据 `artifacts/replay-v6/profile/`。120个测量记录的cProfile累计：fsync平均52.286ms，目录catalog_rows累计17.513ms，JSON canonical累计0.521ms，SQLite execute约0.821ms。累计函数时间存在嵌套，不能相加；剖析只用于定位。

实施两项优化，到此为止：

1. 保留每请求元数据比较及同等有限值/删除/负分检查，将逐行NumPy有限值判断改为一次批量判断。不采用仅凭可变list对象身份跳过内容检查，避免漏掉原地变更。
2. 独立SQLite WAL、synchronous=FULL、持久连接，以单次事务原子写入完整请求。没有异步入队、不合批等待，每次返回前完成提交；目录仍按既有内容寻址文件共享。数据库仅用于隔离记录，不接入生产库。故障传播为显式异常，默认内容路径不依赖它。

正式对照固定四路：未记录、冻结v5文件记录、仅批量校验的文件记录、两项优化的SQLite记录。120请求逐次轮转四路顺序；原v5源文件从Git保存至新目录后加载，使用自身源码校验，不假冒当前源。三种记录器均验证完整分数/top100，最终验收只看预指定SQLite方案对未记录的配对开销，不事后挑选最快方案。每种记录器目录预登记；每请求都写新记录，无推荐结果缓存。

存储同时报告序列化载荷、每事务文件实际增量、全部请求摊销磁盘占用；目录共享字节另列。SQLite以未checkpoint前主库和WAL总量计，包含索引页/帧；同时报告SHM及checkpoint后大小。对≤20原始历史请求，同时检查逻辑大小和事务文件增量≤32KiB，避免以存储实现变化掩盖成本。完成后不以结果触发第三项优化或门槛修改。

SQLite FULL在WAL提交时同步日志的语义依据[官方synchronous说明](https://www.sqlite.org/pragma.html#pragma_synchronous)，并发写入串行与checkpoint行为依据[官方WAL文档](https://www.sqlite.org/wal.html)。这依赖操作系统与存储正确实现同步；本轮进程终止测试不宣称模拟物理断电。
